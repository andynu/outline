# API Strategy: Programmatic Access to Outline Data

## Current API Surface Audit

### Sinatra Server Endpoints (server/app.rb)

| Endpoint | Method | Auth | Purpose |
|----------|--------|------|---------|
| `/health` | GET | None | Health check (data dir exists, inbox writable) |
| `/calendar/:token/feed.ics` | GET | Token in URL | iCal feed of dated items |
| `/outline/data/:doc_id/state.json` | GET | nginx basic auth | Raw document state (read-only viewer) |
| `/outline/data/documents.json` | GET | nginx basic auth | List documents from meta.jsonl |
| `/outline/view` | GET | nginx basic auth | Read-only SPA viewer |
| `/outline/capture` | GET/POST | nginx basic auth | Mobile capture form (HTML) |
| `/outline/api/inbox` | POST | nginx basic auth | Programmatic capture (JSON API) |
| `/outline/api/inbox` | GET | nginx basic auth | List inbox items (optional `?grouped=true`) |

**Assessment**: The server is intentionally thin -- it serves the iCal feed, provides a mobile capture form, and exposes read-only document access for a web viewer. Authentication is handled at the nginx layer (basic auth) or via URL tokens (calendar). This is a reasonable model for a personal/small-team tool.

**Issues found**:
- No explicit CORS headers (fine if behind nginx, but limits direct browser integrations)
- No rate limiting (acceptable for personal use)
- Calendar token validation is simple array membership -- adequate for the use case
- The `/outline/data/documents.json` endpoint reads from `meta.jsonl` which may not exist; the viewer falls back gracefully

### iCal Feed

The iCal feed is generated by the Tauri command `generate_ical_feed` and served as a static file by the Sinatra server. It covers all nodes with a `date` field, includes RRULE for recurring items, marks completed items as `STATUS:COMPLETED`, and uses proper iCal escaping.

**Assessment**: Spec-compliant for the features it uses. The DTSTART is DATE-only (all-day events), which is correct for task dates. The UID format (`{node-uuid}@outline.local`) is stable across regenerations.

**Gap**: The feed is a static file (`feed.ics`) that must be regenerated when data changes. There is no automatic regeneration trigger -- this should be documented or automated (e.g., regenerate on compact, or on a cron).

### Inbox/Capture API

**Endpoint**: `POST /outline/api/inbox`

**Payload**:
```json
{
  "content": "Remember to buy milk",
  "note": "Optional additional context",
  "source": "api"
}
```

**Response** (201):
```json
{
  "success": true,
  "id": "uuid"
}
```

**Assessment**: Clean and functional. The `source` field enables tracking where captures come from (web, api, shortcuts). Error handling returns proper JSON with 400 status. Items are appended to `inbox.jsonl` atomically (append mode).

**Gap**: No authentication on the API itself -- relies entirely on nginx basic auth. For iOS Shortcuts or curl usage, this means embedding basic auth credentials in the request, which is fine for personal use.

## Integration Strategies

### 1. JSONL as API (File-Based Access) -- RECOMMENDED as primary integration path

Since all data lives in flat files under `~/.outline-data/`, external tools can read and write directly without any server.

**Reading data**:
- `documents/{uuid}/state.json` -- full document state, JSON with `{ nodes: [...] }`
- `inbox.jsonl` -- pending capture items, one JSON object per line
- `folders.json` -- folder structure and document-folder assignments

**Writing data**:
- Append to `documents/{uuid}/pending.{source-name}.jsonl` -- operations are replayed on next load
- Append to `inbox.jsonl` -- items appear in the inbox

**Operation format** (for pending JSONL):
```json
{"op":"create","id":"uuid-v7","parent_id":null,"position":0,"content":"<p>New item</p>","node_type":"bullet","updated_at":"2026-02-28T12:00:00Z"}
{"op":"update","id":"existing-uuid","changes":{"content":"<p>Updated</p>"},"updated_at":"2026-02-28T12:01:00Z"}
{"op":"move","id":"existing-uuid","parent_id":"target-parent-uuid","position":2,"updated_at":"2026-02-28T12:02:00Z"}
{"op":"delete","id":"existing-uuid","updated_at":"2026-02-28T12:03:00Z"}
```

**Consistency guarantees**:
- Operations are applied in `updated_at` order during load
- LWW (Last Write Wins) on `updated_at` per node -- later timestamp wins
- Create operations are idempotent (duplicate IDs are skipped)
- File append is atomic on POSIX for small writes (< PIPE_BUF = 4096 bytes)
- The app watches for file changes and reloads automatically

**Recommendation**: Document this as the primary integration path. External scripts should use their own pending file name (e.g., `pending.script-name.jsonl`) to avoid conflicts with the desktop app's writes. Content should be TipTap-compatible HTML (wrap in `<p>` tags at minimum).

### 2. Inbox API (HTTP) -- for mobile and remote capture

Already works well. Recommended enhancements:

- **API key auth**: Add an optional `X-API-Key` header check alongside nginx basic auth, making it easier for iOS Shortcuts and automation tools
- **Batch endpoint**: `POST /outline/api/inbox/batch` accepting `{ items: [...] }` for bulk capture
- **Delete endpoint**: `DELETE /outline/api/inbox/:id` to remove individual items (currently only bulk clear via Tauri command)

### 3. Read API (HTTP) -- for external dashboards and tools

The existing `/outline/data/:doc_id/state.json` endpoint provides full document reads. Additional useful endpoints:

| Proposed Endpoint | Method | Purpose |
|---|---|---|
| `/outline/api/documents` | GET | List documents with titles and node counts (currently exists at `/outline/data/documents.json` but reads from meta.jsonl) |
| `/outline/api/documents/:id` | GET | Get document state (alias for existing state.json endpoint, but returns consistent JSON envelope) |
| `/outline/api/documents/:id/nodes` | GET | Get nodes with optional filters (`?tag=work`, `?has_date=true`, `?checked=false`) |
| `/outline/api/search` | GET | Full-text search across documents (`?q=term&limit=20`) -- would need SQLite FTS access from the server |

**Recommendation**: These are nice-to-haves. For personal use, the file-based read path is more practical. A search API would require the server to open the SQLite FTS database, adding complexity. Defer unless a concrete use case emerges (e.g., an external dashboard).

### 4. Write API (HTTP) -- for remote node manipulation

**Not recommended at this time.** The file-based write path (appending to pending JSONL) is simpler and more reliable. An HTTP write API would need to:
- Accept operations and append them to pending files
- Handle concurrent writes safely
- Return updated state (expensive -- requires full document load)

If needed later, the simplest approach would be a `POST /outline/api/documents/:id/ops` endpoint that accepts an array of operations and appends them to a server-specific pending file.

## Import/Export

### Current Capabilities

| Format | Import | Export |
|--------|--------|--------|
| OPML | Into current doc or as new doc | Full document |
| Dynalist OPML ZIP | Bulk import (all files in zip) | N/A |
| JSON backup | Into current doc | Full document |
| Markdown | N/A | Full document, selection with children |

**Assessment**: Good coverage for the primary use cases. The OPML import handles Dynalist-specific extensions (colors, dates, recurrence, checkboxes). The standalone `import-dynalist.js` script provides a file-based import path that bypasses Tauri.

### Recommended Additions

- **Markdown import**: Parse markdown lists into outline nodes. This is the most commonly requested import format after OPML.
- **Plain text import**: Treat indented text as hierarchy (tab/space indentation). Useful for pasting from other tools.
- **OPML export improvements**: Include note fields as `_note` attribute (matching Dynalist convention) to enable round-trip fidelity.

### Export as Integration Point

The existing `export_json` command produces a complete backup that can be consumed by external tools. This is effectively a read API that produces a snapshot. For automation, a script can read `state.json` directly.

## CLI Tooling

A CLI tool could provide a convenient interface for common operations. Proposed commands:

```
outline search <query>        # FTS search (requires SQLite DB access)
outline add <content>         # Add to inbox (writes to inbox.jsonl)
outline add --to <doc-id> <content>  # Add node to document (appends to pending)
outline list                  # List documents
outline show <doc-id>         # Display document tree
outline export <doc-id> --format md|opml|json
outline import <file> --format md|opml|json [--into <doc-id>]
outline inbox                 # List inbox items
outline inbox clear <ids...>  # Remove processed items
outline compact <doc-id>      # Merge pending into state.json
```

**Assessment**: Valuable for scripting and automation, but not urgent. The file-based access path covers most CLI use cases with standard tools (`jq`, `cat`, etc.). A dedicated CLI would add convenience for search (which requires SQLite) and tree rendering.

**Recommendation**: Defer formal CLI tooling. Instead, document recipes using standard tools:

```bash
# Add to inbox
echo '{"id":"'$(uuidgen)'","content":"Buy milk","capture_date":"2026-02-28","captured_at":"2026-02-28T12:00:00Z","source":"cli"}' >> ~/.outline-data/inbox.jsonl

# List documents
ls ~/.outline-data/documents/

# Search (requires jq)
cat ~/.outline-data/documents/*/state.json | jq -r '.nodes[] | select(.content | test("search term")) | .content'

# Export a document to plain text
cat ~/.outline-data/documents/<uuid>/state.json | jq -r '.nodes | sort_by(.position) | .[].content' | sed 's/<[^>]*>//g'
```

## Webhooks/Notifications

### Current State

The Tauri app has a file watcher (`watcher.rs`) that emits `documents-changed` events to the frontend when files in the documents directory change. This is used for live reload when files sync from other machines.

### Recommendation

No webhook system needed at this time. The file watcher handles the primary use case (sync detection). For external automation triggered by changes:

- **macOS**: Use `fswatch` or `launchd` WatchPaths on `~/.outline-data/`
- **Linux**: Use `inotifywait` on the data directory
- **Cross-platform**: Use the existing Dropbox/Syncthing notifications

If a webhook system is ever needed, the simplest approach would be a small sidecar process that watches the data directory and sends HTTP POST notifications to configured URLs.

## Authentication Model

### Current

- **Calendar feed**: Unguessable token in URL path (`/calendar/{token}/feed.ics`). Tokens configured in `config.json`.
- **Web endpoints**: nginx basic auth (configured outside the app)
- **Inbox API**: Same nginx basic auth
- **File access**: Unix file permissions (no auth layer)

### Recommendation

Keep the current model. For a personal/small-team tool, nginx basic auth + URL tokens is appropriate. If the server were ever exposed to more users:

1. Add `X-API-Key` header support for programmatic access (simpler than OAuth for personal tools)
2. Keep token-based calendar URLs (required by iCal clients that don't support auth headers)
3. Consider session-based auth for the web viewer (cookie after login)

Do not add OAuth or JWT -- the complexity is not justified for the use case.
